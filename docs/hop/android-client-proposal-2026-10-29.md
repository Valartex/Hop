# Android-клиент Hop: исследование и предложение

Дата: 29 октября 2026 года.
Статус: требования уточнены, выполняется реализация и локальная сборка.
APK для проверки и release AAB собраны и проверены.
Испытания на телефоне ещё не выполнены. Исследование ниже не является подтверждением
обхода у оператора.

## Основание

Новый запрос пользователя открывает Android-этап, ранее отложенный в
`requirements.md` и `HOP.md`. Требуется клиент на базе Windows-версии,
отдельные папки платформ, общие модули без копирования и поддержка подключения
в сетях с белыми списками. Проверить новую возможность сначала на Android,
после этого подключить её в Windows.

## Исходное состояние до переноса

- База уже многоплатформенная: C++ / Qt 6 / QML, CMake / Conan; Android
  использует Kotlin / Gradle, JNI и VpnService. Переписывать приложение
  на другой UI-стек для этого запроса не требуется.
- `client/android/` содержит Android-приложение и протокольные модули;
  `client/platforms/android/` — C++-мост. Windows-код распределён между
  `client/platforms/windows/`, `service/`, `client/core/protocols/`,
  `hop/native/` и `hop/tools/`.
- В `client/core/controllers/coreController.cpp` создание каталога,
  координатора соединений и политики маршрутов Hop находится под
  `Q_OS_WIN`. Сборка исходного Android-клиента сама по себе не включает
  весь функционал Hop.
- `LocationCoordinator` запускает текущий исполняемый файл для задач
  провайдера и `hop_tunnel_probe.exe` для проверки туннеля.
  `EndpointHealthController` использует `hop_endpoint_probe.exe` и
  `hop_awg_probe.exe`. Валидация регулярных выражений в `trafficPolicy.cpp`
  тоже вызывает Windows-помощник. Эти зависимости нужно вынести из общего слоя.
- `subscriptionParser.cpp` сохраняет исходный VLESS URI целиком, однако
  `core/utils/serialization/vless.cpp` не содержит отдельного разбора
  XHTTP-параметров. В модели `xrayProtocolConfig.*` XHTTP уже описан.
  Требуется проверить весь путь URI → импорт → сохранение → конфигурация ядра;
  сохранение URI само по себе не доказывает поддержку транспорта.
- Android Xray уже получает JSON-конфигурацию и использует защищённые
  сокеты транспорта. Протоколы запускаются в отдельных Android-процессах.
  Эти границы важны при интеграции нескольких Go runtime.
- Conan фиксирует Android AWG `3.1.20260814` и `amnezia-libxray/1.0.3`.
  Windows Hop использует собственные Xray bindings. Их возможности и версии
  ядра нужно сопоставить до обещания одинаковой поддержки профилей.
- Android applicationId и связанные ресурсы пока принадлежат Amnezia.
  Для Hop необходима своя идентичность приложения и хранилища, чтобы
  установка не заменяла Amnezia и не смешивала настройки.
- В стандартных проверенных местах не обнаружены Android SDK/NDK и JDK 17;
  в `.tools/Qt/6.10.1/` обнаружен только `msvc2022_64`.
  Сборка APK и проверка смартфона не выполнялись. Отсутствие инструментов
  в этих местах не является полной инвентаризацией дисков.

## Что означает обход белых списков

Следует различать ограничения по достижимым IP/подсетям, проверки TLS/SNI/HTTP
и распознавание протокола. Возможны их сочетания. Из этого следует инженерное
ограничение: маскировка не заменяет доступный сетевой путь к входному серверу.
Произвольная замена SNI на разрешённый домен не создаёт такой путь.

Рабочая схема зависит от доступного входного узла, серверной конфигурации,
клиентского транспорта и конкретной сети. Relay/CDN/XHTTP, TLS/Reality,
фрагментирование и параметры AWG следует рассматривать как разные механизмы,
которые могут потребоваться профилю; их нельзя включать всем подряд.
Нельзя считать, что профиль провайдера использует XHTTP, CDN или определённую
фрагментацию, пока это не установлено по конфигурации.

Документация Project X описывает TCP/TLS-фрагментирование как способ
воздействия на анализ трафика в некоторых случаях. Это не подтверждение
универсального обхода ограничений по IP. Современные параметры из документации
Project X также нельзя автоматически переносить в зафиксированное ядро форка:
нужны проверка версии, валидация конфигурации и реальное подключение.

### Amnezia Premium

Официальная документация указывает специальную локацию
«Гренландия [обход БС]». Это подтверждает продуктовый сценарий, но не наличие
отдельного универсального алгоритма в клиентском исходном коде.
FAQ отдельно говорит об отсутствии готового поддерживаемого метода для
Self-hosted. Поэтому первым объектом интеграции должны стать реальные
профили Premium, доступные по подписке пользователя.

Не зашивать название «Гренландия» как вечный технический признак.
Сначала проверить фактические данные API: идентификатор локации, протоколы,
метаданные и получаемую конфигурацию. Если сервер не отдаёт признак назначения,
предусмотреть явную пользовательскую отметку пригодных локаций.
Каталог, доступность API и выпуск конфигурации проверять раздельно;
не выпускать все профили ради обследования каталога и не удалять чужие слоты.

### BlancVPN

Официальная инструкция описывает:

1. Автоподбор в собственном клиенте BlancVPN.
2. Вариант для стороннего клиента: включить «Белые списки и Extra-настройки»
   в личном кабинете, выбрать оператора и обновить подписку в клиенте.
3. При проблемах — фрагментирование в Happ/INCY; на Wi-Fi оно может мешать.

Следовательно, для Hop нужно исследовать обновлённую подписку и необходимые
параметры профилей. Управление настройкой кабинета из Hop — отдельная задача:
публичная инструкция не устанавливает наличие подходящего API.
BlancVPN прямо не гарантирует стабильность при белых списках.

### Подготовка до ограничений

Ограниченная сеть может блокировать не только VPN-вход, но и API/URL подписки,
DNS и адреса обновлений. Нужен последний корректный локальный профиль,
понятная ошибка обновления и возможность подготовить конфигурацию заранее
через рабочую сеть. Новое подключение на ограниченной сети без локального
профиля требует отдельной проверки доступности API провайдера.

## Выполненное разделение исходников

```text
shared/
  client/          C++-ядро, подписки, каталог, пулы, история, QML и тесты
  common/          криптография, логирование, общие политики
  ipc/             контракты обмена клиента со службой
  service/         общий код настольной службы
  native/awgprobe/ общий парсер AWG 3.1, защищённая сессия и проверка
  native/xraybindings/ общий C ABI Xray для настольного клиента
platforms/
  windows/         CMake, нативные адаптеры, протоколы Windows, WFP и служба
  android/         CMake, Gradle, Kotlin, JNI, VpnService и скрипты сборки
build/
  windows/         результаты Windows-сборки
  android/         результаты Android-сборки
```

Существующие сторонние библиотеки и нецелевые платформы upstream сохранены.
Общий C++/QML подключается обеими сборками напрямую; независимой копии Android UI
или бизнес-логики нет. Платформенный `PlatformTask` сохраняет изоляцию подпроцессов
Windows и использует короткоживущую отдельную диагностическую службу Android.
Обработка каталога/выпуска конфигурации провайдера вынесена в общий обработчик.

## Реализованное поведение

- Каталог, HTTPS-подписки, API Amnezia, статические профили, обновления, пулы,
  история, выбор и восстановление используют общую реализацию Windows.
- Интерфейс сохраняет стиль Hop; на телефоне нижняя навигация и компоновка
  для узкого экрана. График позволяет выбрать замер касанием.
- Режимы ограниченной сети: обычный, только отмеченные профили, автоматический
  переход после исчерпания обычных кандидатов. Отметки и разрешённый пул
  сохраняются; произвольные локации вне пула не добавляются.
- Автоматический переход означает последовательность попыток, а не достоверное
  распознавание белого списка. Специальные профили отмечаются пользователем;
  названия стран/провайдеров не используются как эвристика.
- VLESS URI: XHTTP/splithttp, mode, host/path, extra JSON и ALPN; вспомогательные
  выходы Xray, в том числе используемые профилем для фрагментирования, сохраняются.
- Домены/IP/CIDR/DAT компилируются общей политикой. Для AWG с правилами используется
  один системный VPN: Xray направляет VPN-выход в общий пользовательский стек AWG,
  прямой выход — через защищённые физические сокеты. Без правил остаётся штатный
  эффективный AWG backend.
- Проверка активного туннеля привязана к VPN Network; ответ физической сети
  не засчитывается. Endpoint-проверки идут по физической сети. Отмена диагностики
  подтверждается до старта рабочего AWG с тем же ключом.
- Android захватывает IPv6 и блокирует его, как первая Windows-версия;
  полный IPv6-туннель не заявлен. Выделены VPN/direct счётчики Xray.
- Hop имеет отдельный applicationId `io.github.valartex.hop`, хранилище, ярлык
  и уведомление; классы JNI сохраняют техническое пространство имён upstream.
- Сворачивание Activity не отвязывает контроллер соединения; процесс общего
  контроллера привязан к foreground VPN. Принудительное завершение приложения,
  Always-on, восстановление процесса и ограничения Oppo требуют натурной проверки.

## Сборка и проверки

Локально подготовлены Qt 6.10.1 arm64-v8a, Microsoft JDK 17, Android SDK 36,
NDK 27.2.12479018 и закреплённые Conan-зависимости. Скрипт:

```powershell
& platforms/android/scripts/build.ps1
# При проблемах доступа к Maven Central:
& platforms/android/scripts/build.ps1 -MavenCentralMirror https://maven-central.storage-download.googleapis.com/maven2
# Bundle для Google Play (публикация не выполняется):
& platforms/android/scripts/build.ps1 -Release -Bundle
```

Временные инструменты и журналы находятся в игнорируемых `.tools`/`.research`.
Параметры Java/TEMP ограничены процессом сборки, системные настройки не меняются.
Не добавлять keystore, пароли, подписки и полученные конфигурации в Git.

После переноса Windows-клиент и служба пересобраны; прошли 12/12 нативных наборов
(финальная регрессия: 44,55 с): каталог, выбор, подписки, история, UI, политика маршрутов, Windows
network watcher, DAT, endpoint health, жизненный цикл Xray, сериализация XHTTP
и Android routing adapter. Добавлены проверки узких экранов 360/390/600 и
прокрутки настроек при ширине 360; снимки просмотрены.
Общий Go-модуль передал TCP и UDP между двумя локальными зашифрованными узлами
по маршруту за пределами DNS-host; отказ защиты сокета проверен отдельно.
Это автономные тесты, не приёмка смартфона или сети Билайн/МТС.

## Артефакты и оставшаяся приёмка

1. Упаковка завершена. Проверены applicationId Hop,
   versionCode 1, Android 9+/target 36, arm64, отсутствие QUERY_ALL_PACKAGES,
   подпись отладочного APK и ELF-выравнивание всех 111 библиотек на 16 КБ.
   Release AAB проходит Google bundletool validate; подпись для публикации
   подключается позже, публикация пользователем отложена. Артефакты находятся в
   `build/android/artifacts`: `Hop-0.3.0.0-arm64-v8a-release-unsigned.aab` и
   `Hop-0.3.0.0-arm64-v8a-development.apk`. APK получен из того же release AAB
   через bundletool 1.18.3 и подписан локальным тестовым ключом; это не ключ
   публикации. SHA-256, размер и результат проверки ELF записаны в JSON рядом.
2. На Oppo проверить импорт/обновления обоих провайдеров, обычный Wi-Fi и мобильную
   сеть, отмену, ручной/автоматический пул, восстановление, сон/заблокированный экран,
   смену сети и перезапуск процесса. Honor X8 — дополнительная совместимость.
3. Проверить маршруты/DAT, DNS, TCP/UDP, IPv6 и поведение при сбое ядра/переключении,
   включая Direct и системный Always-on/lockdown. При системном lockdown остановка
   VPN блокирует весь трафик, включая прямые исключения; это отличие Android
   от WFP Windows требует согласованной приёмки.
4. Заранее обновить профили BlancVPN после настройки белых списков в кабинете;
   получить реальный специальный профиль Amnezia. Проверить необходимые параметры
   на закреплённом ядре и фактический трафик на Билайне/МТС в Брянской области.
5. После Android-приёмки включить интерфейс нового режима в Windows и отдельно
   проверить его на ограниченной сети. Общая модель/отбор уже переиспользуются.

## Подтверждённые ответы пользователя

- Весь функционал Windows с адаптацией под телефон.
- Oppo A6 Pro, Android 16, Билайн и МТС, Брянская область; также Honor X8.
- USB/ADB и установка APK доступны, телефон подключат позднее.
- Оба провайдера и возможность использовать совместимые профили других.
- Ручной и автоматический режимы.
- APK и release AAB; публикация в Google Play будет позже.
- Согласовано: первая версия использует системную блокировку по желанию;
  собственный Kill Switch с сохранением Direct — следующий этап. Проверено:
  официальная Amnezia Android использует системные Always-on/lockdown,
  встроенного Kill Switch в Android-версии нет. В исходниках его экран скрыт
  на мобильных платформах. Удержание интерфейса при перезапуске ядра возможно;
  защита после остановки всей службы требует системной блокировки Android.
