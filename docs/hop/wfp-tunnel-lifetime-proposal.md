# Изменение времени жизни разрешений VPN-интерфейсов

Статус: пользователь явно разрешил применить и проверить в VM 15 октября.
Патч применён; сборка, 8 CTest и VM-проверки AWG/Direct crash/переключения прошли. Первоначальный отказ
автоматической проверки не обходили: сначала получили отдельное разрешение.

Предлагаемый точный объём:

1. В `service/server/windowsTrafficGuard.cpp` перенести существующие разрешения
   собственных интерфейсов Hop/Hop-TUN из persistent-сессии в отдельную сессию
   `FWPM_SESSION_FLAG_DYNAMIC`; при добавлении указать `persistent=false`.
   Сами условия, вес 1500 и список допустимых интерфейсов остаются теми же.
2. Постоянные блокировки, DHCP, DNS и исключение конкретного VPN-сервера остаются
   в прежней persistent-транзакции. Новые разрешения физического интерфейса не добавляются.
3. В очистке Xray/Wireguard при ошибке использовать существующий `applyTrafficGuard`
   с пустым именем туннеля: блокировки сохраняются, разрешение уже остановленного
   интерфейса удаляется. Явное ручное отключение по-прежнему снимает защиту.
4. Direct остаётся ограничен существующим сокетом: AppID, физический интерфейс,
   исходный адрес, удалённый IP, порт, протокол. Эта часть патчем не расширяется.

Цель: после аварии службы или перезагрузки не оставлять разрешение, привязанное
к старому LUID интерфейса. При замене разрешения возможен краткий перерыв соединений;
ошибка открытия новой сессии оставляет трафик заблокированным.

После разрешения: собрать клиент и службу, повторить AWG/VLESS, Direct, аварийную
очистку и переключение протоколов только в Windows 10 VM через ограниченный агент.
На основном ПК правила WFP и сеть не меняются. Коммитов и публикации не будет.

Подтверждение: `683cba03bc6b479591c2b6dd06b8123f` — после аварии службы
динамических туннельных разрешений 0, Direct-фильтров 0, физический запрос заблокирован.
`deeed9a5def4472e93c32d2362703500` — AWG → VLESS, защита между локациями 13,
резервный Direct HTTP 200, после ручного отключения фильтров 0.
