# Аварийное восстановление собственных IPv4-маршрутов

Механизм из route-recovery-proposal.md применён после явного разрешения пользователя.
На основном ПК служба и recovery не запускались, HKLM/ACL/маршруты не менялись.
Все системные результаты ниже относятся к Windows 10 VirtualBox через ограниченный агент.

`8c7b275e316045768dae3f527411935a`: после аварии собственной службы и её нового старта
созданный Hop /32 удалён, контрольный существовавший /32 сохранён.
`4b4862b8860840a8b8fea4a9310fa61f`: дополнительно сохранён маршрут, метрика которого
изменена тестовым внешним участником после создания. Exit0/recovery0.

API1 RouterWin записывает только CreateIpForwardEntry success; ERROR_ALREADY_EXISTS
не даёт права владения. API2 AWG route monitor и native prefixes используют ту же запись
в процессе основной службы. On-link API2 next-hop0 сопоставляется единственной строке
DIRECT старого API; запись сохраняет наблюдавшиеся полные параметры. Перед удалением
они сравниваются полностью, включая метрики и LUID/GUID интерфейса.

Журнал атомарный, до 4096 строк / 1 МиБ, каталог SYSTEM/Administrators, без reparse points,
один писатель. Volatile HKLM nonce отделяет загрузки ядра. Повреждение/ошибка доступа
не разрешают работу привилегированного IPC. Время между OS-create и записью всё ещё
содержит узкое аварийное окно, а абсолютно идентичную внешнюю замену различить нельзя.
IPv6-маршруты этот журнал не восстанавливает.

Отрицательный `01dd95d4781a463b840a94612a498289`: стартовый VM recovery столкнулся
с lock активной службы. Исправлен только порядок теста: guard-only recovery в VBox,
маршруты активной службы очищаются через штатный IPC ACK; после остановки — журнал.

Отрицательные `37cc8542c35c45bab4e07ec0a7d51a0a`, `5082a1d292064e60819493b60fb16e25`,
`9622a2a570d347249c78683a807572b4`: API1/API2 on-link различие мешало записи AWG.
Подключение останавливалось с 12 persistent guard filters, VM recovery0. Не приняты.

`b67ceb2927d14e3fbc0a611a35ea0eea`: после исправления полный AWG TUN с AllowedIPs0/0
прошёл IP/domain VPN204, GeoSite Block0/Qt2, Direct204 с одним точным сокетным фильтром,
FakeDNS, UDP echo, положительный/отрицательный реальный DNS health. Cleanup ACK1,
guard filters0 после ручного отключения. Fixture не обнаружила транспортную петлю.

Результаты, журналы и точные BUILD-MANIFEST сохранены в `.research/vm-runs`.
Проверка ACL обычным GUI и повторные аварийные AWG/VLESS пробы выполняются отдельно.

`7cfa57683004416b9c1778f8e0fe75d9`: аварии native AWG-процесса и основной службы,
14 persistent filters, VPN endpoint blocked/Qt99 и Direct HTTP200 на обоих шагах,
после recovery сеть восстановилась. `6a4a445d81154e538b9a00328fa13ec8`: реальный VLESS
VPN IP/domain204, Block0/Qt2, Direct200, DNS health1, cleanup0.

`bc81201a09dd4e47bb2168fcc133647a`. Install0, однако recovery3 из-за lock живой
установленной SCM. Исправлен только VM-helper: при точном live SCM image в защищённом
Hop VM Install он сохраняет защиту/журнал до uninstall, не пытаясь забрать владение.
