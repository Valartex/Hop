# Проверка Windows 10 в VirtualBox

## Автономный агент

`Hop-VM-Agent.cmd` запускается пользователем от администратора в гостевой Windows.
Агент работает четыре часа и принимает только `baseline`, `guard-fault`, `stop` из
`HopTestResults/HopJobs/inbox.json`. Он не выполняет произвольные команды.
Подписка вводится скрыто один раз, хранится в памяти и передаётся тесту через stdin.
На каждый тест агент копирует новую сборку, запускает собственную консольную службу,
ограничивает тест 120 секундами и в finally останавливает свои процессы и снимает
постоянные правила только Hop через `hop_guard_recover --vm-test-only`.

`guard-fault` проверяет HTTPS через SOCKS и TUN, отдельное DNS-имя, Direct IPv4,
аварийную очистку без снятия защиты, повторное подключение и завершение своей службы
при активном туннеле. Перед последним сбоем сохранённые маршруты удаляются отдельно:
блокировка должна обеспечиваться WFP, а не недоступным TUN. Затем проверяются
защищённый/прямой IP и доступ после снятия защиты. Это не проверка перезапуска BFE,
загрузки Windows, UDP, AWG или отсутствия всех возможных DNS-утечек.

Вне тестового агента аварийное восстановление требует администратора:
`hop_guard_recover.exe --clear-hop-protection`. Утилита удаляет только фильтры
с одновременным совпадением provider и sublayer Hop.

VM `Windows 10`, UUID `b79c0594-8e7d-42f6-85b6-3b9784efdb1c`.
Перед запуском создан снимок `hop-before-vpn-tests`, UUID
`26fa826b-0581-4d3c-9abb-501a43989980`.
Подключение Amnezia на хосте не отключается и не перенастраивается.

Guest Control не смог запустить процессы под беспарольной учётной записью:
Windows вернула restricted user account. Политика входа и пароль не менялись.
Тест подготовлен для ручного запуска в гостевой Windows.

## Подготовленный пакет

```powershell
& hop/scripts/build-windows.ps1 -Tests -Targets Hop,Hop-service,hop_endpoint_probe,hop_windows_vpn_probe
& hop/scripts/stage-windows.ps1 -Destination build/windows-test -VmTests
```

В работающей VM подключены временные общие папки:

- `\\VBOXSVR\HopBuild` — только чтение, `build/windows-test` на хосте.
- `\\VBOXSVR\HopTestResults` — запись результатов в `.research/vm-exchange`.

После выключения VM временные общие папки исчезают. Скрипт
`hop/scripts/open-windows-vm-test.ps1` запускает эту VM и подключает их заново.
Он не меняет сетевые настройки хоста и не выполняет команды в гостевой ОС.

## Запуск внутри VM

1. В Проводнике гостевой Windows открыть `\\VBOXSVR\HopBuild`.
2. Нажать правой кнопкой `Hop-VM-Test.cmd`, выбрать запуск от имени администратора.
3. Подтвердить UAC внутри VM и вставить HTTPS-ссылку подписки. Ввод скрыт.
4. Дождаться окончания теста; результаты доступны хосту в `.research/vm-exchange`.

Ожидаются `TUN and routing configured` и четыре результата с `HTTP 204, Qt 0`:
`Xray SOCKS HTTPS`, `TUN IPv4 HTTPS`, `TUN DNS HTTPS`, `Network after disconnect`.
Первый запрос проверяет Xray с аутентификацией SOCKS; второй использует заранее
разрешённый IPv4, но проверяет TLS-сертификат и Host как `www.gstatic.com`;
третий включает системное разрешение DNS. Ошибка этапа не скрывает остальные.
В текущем варианте третий этап использует отдельное имя
`connectivitycheck.gstatic.com`, которое тест не разрешает заранее.
Это не заменяет отдельной проверки DNS-утечек и фактического пути DNS-запроса.
Код завершения 0 означает успех всех этапов; 3 — ошибку VPN/транспорта,
4 — ошибку восстановления сети. Это проверка доступности, не скорости скачивания.

Тест копирует пакет в `Program Files/Hop Test` внутри VM, запускает службу
в консольном режиме с повышенными правами, но не регистрирует её в SCM.
Проверяется настоящий `XrayProtocol` клиента: Xray, tun2socks, Wintun,
IPv4-маршруты и WFP. Затем туннель отключается, собственные маршруты удаляются
и выполняется повторный HTTPS-запрос для проверки восстановления сети.
Проверка ограничена 90 секундами. Запущенные тестом процессы завершаются
по своим PID; процессы VPN на хосте не затрагиваются.

`hop_windows_vpn_probe.exe` проверяет модель оборудования VirtualBox и отказывается
менять сеть на физическом хосте. URL поступает через stdin, не через командную строку;
подписка и конфигурация не записываются в файлы. Снимок VM позволяет восстановить
исходное состояние после экспериментов.

Это проверка полного туннеля и штатного отключения, а не достаточная приёмка
Kill Switch при аварии службы/ядра, split routing, DNS/IPv6-утечек или AWG 3.1.

## Полученный результат и следующая проверка

14 октября ручной запуск дошёл до `TUN and routing configured`, затем
`HTTPS failed: HTTP 0, Qt 4`, exit 3. Это тайм-аут, системный VPN не принят.
Первый ложный отказ SMBIOS-проверки исправлен до этого запуска.
Повторный ручной запуск в 18:39 МСК прошёл все четыре этапа с HTTP 204 / Qt 0,
exit 0. Сохранены также stderr/stdout службы; URL подписки не записывается.
[Результат, границы и исправления после чтения логов](vm-validation-2026-10-14.md).

Последующие проверки: [постоянная защита VLESS](windows-guard-validation-2026-10-14.md)
и [реальная подписка AWG 3.1, TCP/UDP и аварии служб](windows-awg-validation-2026-10-14.md).

Локальный AWG-стенд запускается на основном ПК командой
`hop/scripts/test-awg-fixture.ps1`; параметр `-GuardFault` дополнительно завершает
только собственные тестовые процессы внутри VM и проверяет Direct/Block.
Требуется уже запущенный гостевой агент. Стенд на хосте слушает только loopback
и не создаёт системных адаптеров или маршрутов. Реальная подписка для него не нужна.
