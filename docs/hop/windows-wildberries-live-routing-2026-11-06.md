# Wildberries при активном Hop: проверка 6 ноября 2026

Пользователь сообщил о неполной загрузке страницы и разрешил диагностику
текущего подключения основного ПК, включая трассировку. VPN, DNS, маршруты,
правила Hop и службы в ходе проверки не переключались и не изменялись.

## Подтверждённый результат

Установлены клиент и служба 0.2.0.21; контрольные суммы совпадают с принятой
установкой. Активны Hop-TUN (1420) и транспортный интерфейс Hop/WireGuard.

Сохранена включённая политика: PRIVATE, RU, CATEGORY-RU, AVITO → Direct;
остальной трафик → VPN. Кэш DAT совпадает с контрольными суммами источников,
последняя успешная проверка источников — 6 ноября. Все 11 доменов, замеченных
при первоначальной загрузке главной страницы, покрываются CATEGORY-RU:
wildberries.ru, wbbasket.ru, geobasket.ru и соответствующие поддомены wb.ru.
Нового отсутствующего доменного правила среди них не найдено.

Для отдельных контрольных запросов подтверждена не только категория, но и
реальная исходящая TCP-сессия службы Hop. Запросы поступали обычным системным
путём через FakeDNS/TUN; принудительный обход Hop или SOCKS не применялся.
Сопоставлены появление TCP-сессии PID 26896, чтение полного ответа и приращение
счётчика hop-direct встроенного ядра. Иные фоновые счётчики могли расти
параллельно, поэтому их общий прирост не приписывается проверяемому запросу.

## Что остаётся не установлено

Во встроенном диагностическом браузере оболочка и баннеры главной страницы
загрузились, товарного блока не было; после ввода поиска остался индикатор
загрузки без результатов. Это воспроизводит видимый симптом, но не доказывает
совпадение зависшего запроса с пользовательским Firefox.

Ошибок JavaScript в доступном журнале не появилось. После повторной загрузки
инструмент управления вкладкой дважды перестал отвечать; дальнейшие действия
с браузером остановлены. Firefox был свёрнут, получить его сетевую панель
через доступный интерфейс не удалось. Пользователю отправлена просьба
развернуть Firefox на проблемной странице для сопоставления точного запроса.

Обычный tracert к 85.198.77.24 и 213.184.155.75 не получил ответов на первых
пяти переходах (без разрешения DNS, ограничение ожидания 250 мс).
ICMP в этой архитектуре не повторяет проксируемое TCP-соединение, поэтому
эти тайм-ауты не доказывают ни маршрут через VPN, ни потерю HTTPS.
Пакетного захвата нет: pktmon status получил отказ в доступе; UAC и захват
без необходимости не запускались. Маршрут контрольных HTTPS подтверждён
TCP-сессиями, интерфейсом/шлюзом и счётчиками ядра, а не ICMP.

Точный зависший запрос пользовательской страницы, причина его ожидания и
исправление всего сайта пока не установлены. Менять правила на основании
успешных контрольных загрузок или объявлять проблему устранённой нельзя.

## Продолжение после сообщения о сравнении с Happ

Пользователь уточнил: при той же локации BlancVPN через Happ сайт работает,
через Hop — нет. Это основание продолжать исследование клиентского пути,
а не закрывать вопрос по успешным контрольным файлам. Предыдущее завершение
диагностики из-за остановки управления Firefox не означало завершение
сетевой проверки.

Проверен результат попытки пакетного захвата: он не стартовал.
Первый скрипт имел несовместимую с Windows PowerShell 5 кодировку;
после её исправления обнаружена отдельная ошибка декодирования UTF-8
вывода pktmon как OEM. Из-за этого скрипт безопасно остановился на
проверке исходного состояния, до добавления фильтров. Оба дефекта помощника
исправлены. Разбор скрипта и корректное чтение русскоязычной справки pktmon
проверены именно в Windows PowerShell 5. Последующий запрос UAC Windows
вернула как отменённый пользователем; повторной попытки без нового указания
не выполнялось. Пакетных данных по-прежнему нет, чужой захват не останавливался.

Ограничение управления Windows-браузером относится к Firefox; оно не
предотвращает дальнейшую работу с разрешённым встроенным браузером.
После исчезновения старых вкладок создана новая диагностическая вкладка.
Около 22:20 МСК главная страница в ней загрузила 28 карточек товаров;
после поиска «ноутбук» появились 56 карточек и пять видимых загруженных
изображений geobasket.ru. Ошибок JavaScript в доступном журнале нет.
Вкладка сохранена для последующего сравнения.

При этой успешной загрузке система показывает запущенную службу
AmneziaWGTunnel$Hop и активный интерфейс Hop/WireGuard. Сохранён выбранный
API-профиль с суффиксом nl; по реализации LocationCatalog это API-локация,
а не обычная запись HTTPS-подписки VLESS. Режим — Automatic, два приоритета.
Следовательно, эту загрузку нельзя выдавать за успешную проверку BlancVPN.
Нельзя также утверждать, что пользовательский сбой устранён: исправления
приложения не выполнялись. Пользователю отправлена просьба вручную подключить
проблемную локацию BlancVPN в ручном режиме для точного воспроизведения.

## BlancVPN: подтверждённое воспроизведение и успешный запуск диагностики

После сообщения пользователя о подключении BlancVPN повторён UAC.
AmneziaWGTunnel$Hop больше не работает, остались основной Hop-service и
tun2socks; Hop-TUN имеет MTU 1420. Метрики нового ядра доступны на localhost:60126.

Исправленный помощник выполнил 40-секундный захват, завершился с completed=true,
error=null и удалил собственные фильтры. Исходное состояние было «монитор не
запущен / фильтров нет». Фильтровались два наблюдавшихся диапазона CDN и три
текущих FakeDNS-адреса доменов WB. Счётчики указали 1043 входящих и 561 исходящий
пакет Wi-Fi, 2045 входящих и 1418 исходящих пакетов TUN. Однако ETL 13 312 байт
содержит только служебные события, текстовый экспорт — 2032 байта без пакетов.
Это не пригодная для разбора пакетов трасса; по ней не делается вывод
об отдельных потерях или ретрансляциях. Причина отсутствия событий не установлена.

В той же сохранённой встроенной вкладке при BlancVPN главная страница
повторно осталась без карточек товаров. Видимые баннеры спустя ожидание
загрузились, но карточек по-прежнему 0. В доступном журнале нет ошибок JS.
По сравнению с успешной загрузкой AmneziaWG отсутствуют наблюдавшиеся
модули B2B и запрос рекомендаций u-recom. Отсутствие ресурса в инвентаре не
доказывает, что именно его загрузка завершилась сетевой ошибкой.

Контрольные проверки при активном BlancVPN:

- 15 параллельных HTTP/2-запросов прошли с полной длиной тела и HTTP 200,
  0,103–0,146 с;
- четыре HTTP/3/QUIC-запроса к модулю и WebP прошли с HTTP 200 за 0,257–0,332 с,
  как с обычными параметрами, так и с размером начального пакета 1200 и без PMTUD;
  SHA256 совпали с контрольными HTTP/1.1;
- запросы A, AAAA, HTTPS для трёх доменов через FakeDNS ответили за 2–4 мс;
  контрольный Quad9 через VPN/9953 — за 180–199 мс, без тайм-аутов;
- HTTPS-загрузка с принудительно указанным старым FakeDNS-адресом сохранив
  нормальную проверку сертификата прошла, как и с новым адресом. Простая
  гипотеза «любой старый FakeDNS-адрес ломает TLS» не подтвердилась.

Контрольные прогоны не устанавливают причину зависания страницы. Нельзя
объявлять общий отказ QUIC, DNS или исправление WB. Приложение и системные
настройки не изменялись. Для получения статуса конкретного зависшего запроса
у пользователя запрошен локальный HAR. Доступный интерфейс встроенного браузера
не предоставляет журнал запросов, а автоматизация Firefox ограничена инструментом.
Помощник HAR выводит только URL без значений query, время, статус, протокол и IP;
cookies, заголовки авторизации и содержимое ответов не выводятся.
