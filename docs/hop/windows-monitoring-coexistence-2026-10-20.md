# Приёмка 0.2.0.8: совместимость сети и мониторинг

Работа по девяти замечаниям от 20 октября. Изменения реализованы и проверены
в Windows 10 VM; локальное обновление и настройка DNS VM завершены.
Рабочий RDP и интернет VM при Hop на основном ПК требуют пользовательской проверки.

## Уточнения пользователя

- Официальный OpenVPN на основном ПК подключается, но RDP в рабочую сеть
  не проходит, пока включён Hop. При отключении Hop доступ восстанавливается.
- Цель RDP: 192.168.1.132:3389. OpenVPN публикует маршрут 192.168.1.0/24,
  а Hop создавал более точные /25 той же локальной подсети; приоритет получал Hop.
- T1/T2: задержка непрерывно выше T2 в течение T1 — повод переключиться.
- Основной ПК: только чтение состояния, никаких сетевых переключений агентом.
  Системные проверки исправлений — в Windows 10 VirtualBox.

## Изменения

- Статус загрузки/ошибки/успеха относится к заголовку конкретной подписки.
- В блоке подключения показывается замер активной локации; кнопка отключения
  отличается цветом. При отрицательном замере отображается «Нет ответа».
- Сбор статистики: все / пул / активная / отключено. Область определяет
  фоновые проверки и запись истории; существующая история не удаляется.
  Контроль работающего туннеля нужен для переключения и текущего индикатора
  даже при выключенной записи истории. API-профили ради замеров не выдаются.
- T1: 15–3600 секунд, T2: 1–10000 мс. Начальные значения 60 секунд и 1500 мс.
  Контроль по последовательным замерам, обычный интервал 15 секунд плюс время
  самой пробы. Это дискретное наблюдение, а не непрерывное измерение каждого пакета.
  Ответ ≤ T2 и отсутствие локальной сети сбрасывают отсчёт. Таймаут ответа
  считается превышением. Ручной режим не начинает автоматический перебор.
- Перед автоматическим перебором выполняется обновление источника текущей
  локации без снятия защиты и без отключения туннеля для самой загрузки.
  Успех даёт одну повторную попытку текущей локации. Если загрузка не удалась,
  Hop очищает только свой туннель с сохранением Kill Switch и повторяет загрузку
  один раз без сбойного туннеля: точечные разрешения контрольного канала не
  обходят маршруты Windows. После второго отказа — следующий кандидат пула.
  Цикл ограничен, устаревшие ответы не влияют на новую сессию.

## Сеть: узкое исправление, требующее VM-проверки

В прежней реализации локальные маршруты перехватывались даже при первом
безусловном PRIVATE → Direct. WFP также блокировал трафик другого адаптера.
Теперь только RFC1918-префиксы из начальных IP-правил Direct могут использовать
обычную таблицу Windows, в том числе более точные маршруты рабочего OpenVPN.
При встрече доменного правила, VPN или Block оптимизация прекращается.
Публичные сети, IPv6 и произвольные интерфейсы целиком не разрешаются.
Предел — 64 частных префикса; при превышении используется прежний защищённый путь.
DNS-блокировки имеют больший вес и сохраняются. При PRIVATE → Block локальная
сеть снова перехватывается общим маршрутизатором и блокируется.

Разрешение собственных TUN-интерфейсов проверяет IP_NEXTHOP_INTERFACE,
а не IP_LOCAL_INTERFACE: последний связан с адресом bind(), а не путём пакета.
Оба условия поддерживаются ALE_AUTH_CONNECT на целевых Windows:
https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-conditions-available-at-each-filtering-layer
https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-
Динамическое время жизни разрешения и ограничение собственными интерфейсами
сохранены. Основной ПК для проверки этого исправления не перенастраивается.

Причина сегодняшнего отказа Amnezia пока не установлена: журнал Hop отключён,
сообщения об ошибке нет. Нельзя приписывать отказ провайдеру или лимиту слотов
без нового подтверждения.

Для VM пользователь согласовал штатное выключение/запуск и включение NAT
DNS Host Resolver после сетевых проверок. NAT сейчас берёт список DNS хоста,
в журнале были 100.64.0.1 / 8.8.4.4 / 192.168.1.1. При смене VPN он может
использовать недоступный сервер. Режим системного резолвера документирован Oracle:
https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/networkingdetails.html
Это настройка конкретной VM, не автоматическая перенастройка чужих приложений Hop.
Подтверждение интернета при работающем Hop на основном ПК остаётся пользовательским.

Отдельная проба с явным bind к исходному IPv4 не получила DNS-ответ через TUN,
хотя обычный VLESS HTTPS работал. Изменение weak-host флагов собственного адаптера
не помогло и удалено из продукта. Физические адаптеры не менялись; VM-стенд
проверяет отсутствие экспериментальных флагов на своём Hop-TUN при замене runtime.

## Оставшаяся пользовательская проверка

При первом правиле PRIVATE → напрямую, подключённых Hop и рабочем OpenVPN
проверить RDP к 192.168.1.132:3389. Проверить доступ к сайтам из Windows 10 VM
при Hop на основном ПК. Эти подключения на основном ПК автоматически не выполнялись;
VM-проверки не заменяют приёмку в реальной рабочей сети.
