# Windows: ручной выбор в автопуле и диагностика маршрутов, 4 ноября 2026

## Выбор локации

В установленной 0.2.0.20 `SelectionSession::start()` очищал `m_preferred`.
После выбора второй или последующей локации запуск режима `Automatic`
поэтому всегда выбирал первого разрешённого участника пула.

В кандидате 0.2.0.21 выбранная локация задаёт первую попытку в этом режиме.
Она используется только если входит в текущие допустимые кандидаты:
исключения, членство в пуле и ограничения сети сохраняются. При недоступности
клиент ждёт подтверждения очистки транспорта и продолжает обычный перебор.
Приоритеты пула не переписываются. Режимы общего списка и минимальной
задержки продолжают выбирать по своим правилам.

Регрессия до исправления: выбран `b`, фактическая первая попытка `a`.
После исправления весь `TestSelectionSession` прошёл: 25 проверок с учётом
инициализации/завершения. Отдельно проверено, что недопустимый ручной выбор
не обходит исключения и сетевые ограничения.

## Wildberries и Avito

Прочитаны только ключи политики маршрутов и источников DAT основного ПК.
Настройки и подключения не менялись. Сохранённая политика включена:

1. GeoIP `PRIVATE` — напрямую.
2. GeoIP `RU` — напрямую.
3. GeoSite `CATEGORY-RU` — напрямую.
4. GeoSite `AVITO` — напрямую.
5. Остальной трафик — VPN.

В локальном GeoSite 84 категории; `CATEGORY-RU` содержит 1145 правил,
`AVITO` — 5. SHA256 проверенных файлов:

- GeoIP: `48b8e1e2118026ac5d53a6ab01774b6392717d640146d3b4851cf8fc9882e72d`.
- GeoSite: `10d125d09e946d6cf554ef5b32dba9311e59ef77067021d50385814c10db25ea`.

При открытии главной страницы Wildberries в диагностическом браузере
обнаружено 243 ресурса на 25 доменах: HTML, скрипты, стили, шрифты,
изображения и запросы данных. Все 25 доменов покрываются сохранённой
категорией `CATEGORY-RU`, в том числе `wbbasket.ru`, `geobasket.ru`,
`wb.ru` и их наблюдаемые поддомены. Это проверка покрытия правил,
а не подтверждение успешной загрузки через работающий Hop:
на основном ПК во время диагностики Hop был закрыт, работал Happ.

`avito.ru`, `avito.st`, `avito.com` и `avito.tech` уже входят в `AVITO`.
Открытие самой страницы Avito диагностический браузер заблокировал;
обход ограничения не выполнялся. Покрытие всех её фактических запросов
не проверено. Добавлять новые домены без наблюдаемого сбойного запроса
оснований пока нет.

Новый изолированный Go-тест запускает настоящее ядро с FakeDNS,
доменным правилом Direct, привязкой исходного сокета и локальным UDP echo.
Проверены три последовательных пакета через один поток. Они дошли и
вернулись, включая разрешение синтетического адреса FakeDNS в реальный
адрес стенда. Системные маршруты, DNS, WFP и службы тест не изменяет.

На этапе первичного аудита причина пользовательского сбоя загрузки не была установлена.
Нужны конкретный сбойный запрос и ошибка браузера при активном Hop;
различия между DNS браузера, DNS внутри VPN, маршрутом сокета и
ответом CDN нельзя определить только по составу DAT.
Основной ПК для сетевого воспроизведения автоматически не переключался.
На этапе первичного аудита системная проверка в VM ещё не была выполнена.
Продолжение после запуска пользователем нового агента приведено ниже.

## Продолжение: потеря UDP из-за MTU

Пользователь уточнил: преимущественно не загружаются изображения;
после отключения Hop они снова доступны. С его новым сеансом VM-агента
выполнены системные проверки на Windows 10.

В первом прогоне `afdbf6f6a9a24e54ab0ff368afc941ed` CDN изображения
вернул HTTP 200 через TUN, но тело осталось пустым до тайм-аута;
через SOCKS тот же файл загрузился. Следующие прогоны с тем же файлом
проходили. Один этот тайм-аут не доказывает его конкретную причину.
Адреса CDN из DNS до VPN и через VPN совпадали.

Обнаружен самостоятельный дефект клиента: IP MTU адаптера Hop-TUN в Windows
равен 65535, а закреплённый tun2socks 2.6.0 через wireguard-go использует
буфер 1420 байт. `NativeTun.Read()` копирует в этот буфер только помещающуюся
часть пакета, поэтому больший пакет теряет хвост.

Воспроизведение `7e9d4c92b2e241e48e9d5223289e832a` проверило именно этот
эффект с контролируемым UDP echo на loopback хоста через NAT тестовой VM.
Отдельный маршрут только внутри VM принудительно направлял запросы в TUN;
содержимое ответов сравнивалось побайтно. Проверка A/B/A исключила простое
прогревание соединения:

| Полезная нагрузка UDP | MTU 65535 | MTU 1420 | Возврат MTU 65535 |
| --- | --- | --- | --- |
| 1232 байта | проходит | проходит | проходит |
| 1372 байта | проходит | проходит | проходит |
| 1400 байт | теряется | проходит | теряется |
| 1452 байта | теряется | проходит | теряется |
| 4096 байт | теряется | проходит | теряется |

`RouterWin::createTun()` теперь задаёт и проверяет IP MTU 1420 только
на собственном Hop-TUN. Сохраняются остальные прочитанные свойства
интерфейса; SitePrefixLength для IPv4 обнуляется по требованиям API.
При ошибке настройка VPN прекращается с обычной очисткой.
Физические адаптеры и интерфейсы других VPN не меняются.

Источники поведения:

- tun2socks 2.6.0, `core/device/tun/tun_wireguard.go` и `core/device/iobased/endpoint.go`;
- закреплённый wireguard-go `f333402bd9cb`, `tun/tun_windows.go`, forcedMTU 1420 и ограниченный `copy` при чтении;
- [Microsoft: SetIpInterfaceEntry](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-setipinterfaceentry).

После обновления именно установленной в VM службы, без ручного изменения MTU,
прогон `781a10b26dfe466c94e8e775f8c661b1` подтвердил:

- MTU 1420 до начала запросов;
- все пять размеров UDP проходят;
- 12 загрузок изображений через TUN (HTTP/2 и HTTP/1.1) и 2 через SOCKS
  проходят с HTTP 200, полным WebP и тем же SHA256, что до VPN;
- штатное отключение, завершённая очистка и 0 фильтров защиты.

Дополнительно изолированный Go-тест провёл 32 параллельные загрузки по 1 МиБ
через Direct/FakeDNS/TLS с проверкой SHA256 и освобождения разрешений сокетов.
Это не полноценная HTTP/3 проверка браузера. Ошибка MTU может объяснять
сбой UDP/QUIC, но конкретный запрос пользовательского браузера ещё не получен,
и утверждать, что любые сбои обоих сайтов устранены, пока нельзя.

Отрицательные и промежуточные результаты сохранены. Один диагностический запуск
не успел получить ключ за прежние 40 секунд при копировании комплекта;
ожидание ограниченно увеличено до 90 секунд. В отдельном прогоне baseline DNS
VM был недоступен ещё до VPN; этот результат не приписывался Hop.
Через IPC собственной установленной службы внутри VM выполнено восстановление
сохранённых DNS, собственных маршрутов и очистка DNS-кэша, затем baseline прошёл.
Консольный дубликат службы не мог открыть занятый журнал маршрутов;
системные проверки использовали уже установленную службу SCM.

Три выгрузки pktmon содержали только заголовки pcapng. Их нельзя использовать
как доказательство маршрута пакетов или отсутствия потерь.
