# Продолжение Windows 18 октября 2026

## Восстановление подписок

В `client/tests/testHttpSubscriptions.cpp` добавлены два сценария с отдельным
дочерним процессом и синтетической подпиской. Процесс завершается через `_Exit(91)`:

- перед проверяемой записью `Servers/serversList`;
- после успешного `setValueChecked` / `sync`, до публикации нового снимка репозиторием.

Новый экземпляр хранилища и репозитория получает соответственно целый прежний
или целый новый список, корректный сервер по умолчанию и описание. Деструкторы
дочернего процесса не выполняются. Проверка отказа записи через существующий
`SnapshotFailureSettings` также остаётся в наборе: не публикуется новый снимок,
не отправляется сигнал обновления, сохранённый список остаётся прежним.

`HopHttpSubscriptions`: PASS, 0.84 с. Отдельный подробный прогон двух аварийных
случаев: 4 PASS с init/cleanup, 0 FAIL, 204 мс;
`.research/snapshot-crash-2026-10-18.txt`.
Тесты используют отдельные QSettings с префиксом `Hop-Snapshot-Crash-` и
отключённое шифрование синтетических данных. Это проверка границы сохранения,
а не внезапного отключения питания, сбоя диска или DPAPI.

## Разделение Windows-идентичности

Сверены `hop/scripts/build-windows.ps1`, фактический `CMakeCache.txt`,
`build/windows/client/version.h` и определения в `build.ninja`:

| Назначение | Hop |
| --- | --- |
| Приложение / организация QSettings | Hop / Hop |
| Служба | Hop-service |
| Экземпляр GUI | HopInstance |
| IPC | local:HopVpnIpcInterface |
| QtKeychain | Hop-Keychain |
| Интерфейсы | Hop / Hop-TUN |
| Native daemon pipe | Hop-VpnDaemon |
| AWG служба / защищённый pipe | AmneziaWGTunnel$Hop / ...AmneziaWG\Hop |
| Upstream app updater / app split driver | отключены |

Сохранённый префикс протокольного AWG runtime не является общим идентификатором:
суффикс интерфейса Hop разделяет службу и pipe. WFP provider/sublayer, журнал
маршрутов и проверка владельца уже проверены ранее в VM. Другие платформы отложены.

## Установщик: подготовка проверки

Прежняя схема каждый раз создавала новый ProductCode с неизменной версией 0.1.0.
WiX по умолчанию позволяет двум таким продуктам сосуществовать. Новая схема:
версия из `hop/packaging/windows-version.txt` (0.1.1), ровно три числовых поля
Windows Installer, постоянный UpgradeCode и ProductCode, детерминированный по версии.
При изменении распространяемого пакета версию необходимо повышать. Каталог
установки сохраняется в собственной записи HKLM и читается следующими версиями.

`MajorUpgrade` остаётся внутри транзакции, после `InstallInitialize`:
при ошибке должно быть возможно восстановить прежнюю установку.
Прежний проверенный MSI90ee сохранён в `.research/accepted-builds/90eeb429`.

Подготовлены ограниченные сценарии VM `InstallerUpgrade`, `InstallerRollback`,
`InstallerDowngrade`. Они проверяют ровно один продукт с собственным UpgradeCode,
версию, путь/auto-start SCM, сохранение тестовой защиты; для отрицательных случаев
также сравнивают SHA256 GUI/службы/agw/манифеста с прежними файлами. Снятие тестовой
защиты с результатом guard0 входит в успешное завершение сценария.

Отдельный `build_rollback_fixture.py` добавляет только в тестовый MSI ошибку
`HOP_TEST_ROLLBACK_AFTER_EXECUTE` после `InstallExecute`, до `InstallFinalize`.
Это позволяет проверить откат уже исполненной замены файлов и служб. Такой MSI
намеренно не устанавливается успешно и не является пакетом пользователя.
Вложенные MSI и VM-скрипты исключены из пользовательского payload.

Генератор отвергает четырёхкомпонентную версию 0.1.1.1 до создания WXS.
WiX успешно скомпилировал пакет 0.1.1 и тестовый 0.1.2. Декомпиляция фактического
0.1.1 подтверждает версию, ProductCode, собственную запись InstallLocation и
условие снятия защиты только при явном удалении, а не при upgrade.
Финальный обычный MSI0.1.1:
`c40d8a43bba6631ab4adac76514ecc5bc90cfe3bd026a9b33e6e7eb0dd07c896`.
Тестовый MSI0.1.2:
`834907e9c06e5177bc0e728b75b5ead64f5925dc7de741b846af33b08f54e0fb`.
Оба подготовлены в общей папке; хеши EXE/DLL stage совпадают с BUILD-MANIFEST.
SBOM `build/sbom-0.1.1`: 204 файла/286 компонентов, официальный CycloneDX1.6
прошёл проверку; версия берётся из WXS, включены Go-зависимости AWG-проверки.
Это ещё не системная приёмка обновления/отката: нужен вручную запущенный VM-агент.

Основание поведения MSI: [Microsoft ProductVersion](https://learn.microsoft.com/windows/win32/msi/productversion),
[WiX MajorUpgrade](https://docs.firegiant.com/wix3/xsd/wix/majorupgrade/).
Сеть, Amnezia, службы и драйверы основного ПК не менялись. Системные сценарии
предназначены только для Windows 10 VirtualBox; boot/always-on защита вне объёма.
